# Admin Panel Upgrade — Task Checklist

Derived from `ADMIN_UPGRADE_BRIEF.md` §2 (revised priority order). Same cadence as the
client-panel redesign: one task at a time — read the real code first, build, deploy,
verify with Playwright against a throwaway account, clean up test data, check the task
off with a note on what was actually found, then report and wait.

Ordered by risk, not by visibility. Security and money integrity precede cosmetics.

## Phase B — Financial integrity

- [x] **B1. Money-path transaction audit.** Audited every route touching `virtual_wallets`/`wallet_ledger`/`positions` in `adminApi.ts`, `api.ts`, `ExecutionEngine.ts`. `POST /funds/requests/:id/approve` was re-verified genuinely safe (locks both rows, status-guards inside the lock) — it was the template the rest were brought up to match. Found and fixed:
  - **`POST /funds/requests/:id/reject`** — no transaction, no lock, an unconditional `UPDATE ... WHERE id=$1`. A concurrent `/approve` could commit first and this would silently overwrite `status` from `APPROVED` back to `REJECTED` after money had already moved, corrupting the audit trail with no way to tell from `fund_requests` alone that the deposit/withdrawal actually happened. Fixed: `UPDATE ... WHERE id=$1 AND status='PENDING' RETURNING id`, 409 if no row matched.
  - **`POST /customers/:id/funds`** — wrapped in `withTransaction` but the balance arithmetic (`currentCash + amt`) happened on an unlocked read *before* the transaction opened — a classic lost-update: two concurrent calls could both read the same stale balance and each overwrite the other's result while the ledger ends up with two rows that don't sum to the real change. Fixed by replacing the hand-rolled UPDATE+INSERT with `VirtualWalletLedger.adminAdjustBalance` (which takes `SELECT ... FOR UPDATE` and computes the new balance from the locked read) — this also changes DEDUCT-beyond-balance from silently clamping to ₹0 to correctly rejecting with 409, since silent clamping was itself an audit-trail lie ("deducted ₹9,999,999" when only ₹2,000 actually moved).
  - **`POST /positions/:id/edit`** — updated `positions.net_qty` directly without ever calling `recomputeUsedMarginForUser`, unlike every other code path that changes position size. Left `used_margin` permanently stale after an admin qty correction, overstating the user's buying power until an unrelated order event happened to trigger a recompute. Fixed: call the recompute immediately after the position UPDATE.
  - **`POST /positions/:id/square-off`** (most severe finding) — computed `exitSide`/`exitQty` from an unlocked read *before* the transaction, and `PortfolioService.recordExecutionInTransaction`'s "position was flat" branch treats a second square-off of an already-closed position as a brand-new trade, not a no-op. Two concurrent square-off clicks could fabricate a phantom opposite-side position and double-apply P&L/margin settlement. Fixed: re-read `net_qty` under the same `FOR UPDATE` lock at the top of the transaction and abort (409, no money moved) if it no longer matches the outer read.
  - **`POST /orders/:orderId/cancel` and `/reject`** — same shape as `/reject` above: unconditional `UPDATE ... WHERE id=$1` inside the transaction, no status predicate. A concurrent fill (`ExecutionEngine`'s 500ms loop) could commit `status='FILLED'` first, and the cancel/reject would silently overwrite it back, hiding that a real trade and cash movement happened. Fixed: `WHERE id=$1 AND status IN (...)` + `RETURNING id`, 409 on no match.
  - **`ExecutionEngine.executeOrder`** — its idempotency guard was a plain unlocked `SELECT` with no DB-level backstop (`executions.order_id` has no unique constraint); two near-simultaneous calls (an admin force-execute racing the engine's own sweep) could both pass it and double-fill the same order. Fixed: made the `orders` status transition to `FILLED` itself the atomic guard (`UPDATE ... WHERE status IN ('ACCEPTED','PENDING') RETURNING id`, first statement in the transaction) rather than a separate unconditional UPDATE later in the same function.
  - **`POST /funds/direct-adjust`** — the balance mutation (via `adminAdjustBalance`) and the `fund_requests` audit-trail insert were two independently-committing operations; if the second ever threw, a real balance change would be left with no matching request record. Fixed: extended `adminAdjustBalance` to accept an optional external transaction `client` so both writes commit or roll back together.
  - **`POST /funds/reset-margin`** (`api.ts`) — three unprotected statements with no shared transaction, and the ledger row hardcoded `balance_before` to `0` regardless of the wallet's real prior balance. Fixed: wrapped in `withTransaction`, locks the wallet row first, uses the real prior balance. **While fixing this, testing surfaced a genuine pre-existing bug, not introduced by this change**: `'MARGIN_RESET'` was never a permitted `wallet_ledger.transaction_type` under the table's CHECK constraint, so this route's ledger insert had always thrown — added migration `023_wallet_ledger_margin_reset_type.sql` to add it as a legal value.
  - **Flagged, not changed** (business/policy calls, not atomicity bugs): `POST /funds/instant`'s `DEPOSIT` branch lets any logged-in user instantly credit their own wallet, fully bypassing the admin-approval flow — plausibly intentional for a paper-trading simulator (self-service practice capital), but worth the user's explicit call on whether it should be gated. Dead duplicate route registrations of `POST/GET /funds/request` and `/funds/my-requests` at `api.ts:1542/1571` (Express never reaches them) — cosmetic, not a money-correctness issue.
  _Verified in production_ against real concurrent requests (not just code review): a double-click race on `/positions/:id/square-off` — exactly one of two simultaneous requests succeeded, the other got 409, final position/wallet state showed the P&L applied exactly once (no phantom position). A genuine concurrent race between `/orders/:id/cancel` and `/orders/:id/reject` on the same order — exactly one won, order ended in a single consistent status. `/funds/requests/:id/reject` on an already-approved request — 409, status stayed `APPROVED`. `/customers/:id/funds` ADD and over-limit DEDUCT — correct new balance / correct 409. `/positions/:id/edit` — `used_margin` changed from stale `0` to the correct recomputed value after an edit. `/funds/direct-adjust` — balance and audit row both present. `/funds/reset-margin` — succeeded post-migration with the real `balance_before` in the ledger row. All test users/positions/orders/wallets/ledger rows cleaned up afterward; `tradegrow_app` healthy throughout.
- [x] **B2. Withdrawal workflow hardening.** Re-read the full `/funds/requests/:id/approve` state machine (deposit + withdrawal branches): both lock the fund-request row and the wallet row `FOR UPDATE` inside one transaction, withdrawal has an explicit buying-power check and a negative-balance guard before debiting, large/non-privileged-role withdrawals escalate to `TIER_2_SENIOR` rather than silently failing or auto-approving, and deposits are protected against a duplicate reference-note being approved twice. B1's fix to `/reject` (atomic `WHERE status='PENDING'`) closes the concurrent-approval/reject race for this same state machine. One real gap found and fixed: **`/reject` never called `logAuditAction` at all** — every state transition on a fund request except rejection had an audit trail entry; a rejected withdrawal/deposit request left zero record of who rejected it or why. Added the missing `logAuditAction('REJECT_FUND_REQUEST', ...)` call.
- [x] **B3. Ledger-derived balances.** Added `GET /admin/finance/ledger-reconciliation` (new, `RESERVES_RECONCILE` permission) — for every user, compares `virtual_wallets.cash_balance` against the `balance_after` of their most recent *cash-balance-mutating* `wallet_ledger` row (explicitly excluding `MARGIN_BLOCK`/`MARGIN_RELEASE`, which never touch `cash_balance` at all — they reuse the same `balance_after` column to record post-op buying power instead; including them produced a confirmed false positive during testing). _Run against real production data_: initially found 2 drifted users. One was the MARGIN_BLOCK false positive above (fixed by excluding those types, re-ran, resolved). **The other is a genuine, real finding**: one live user's `cash_balance` was silently reset to the default ₹10,00,000 by the exact `/funds/reset-margin` bug B1 found and fixed (the ledger insert always threw before migration `023`, so the balance-changing `UPDATE` committed with zero ledger trail) — this happened for real, today, before the fix was deployed. Their balance is presumably correct (they took a real reset action); it's the historical ledger row that's permanently missing. **Backfilled per explicit user instruction**: inserted the missing `MARGIN_RESET` `wallet_ledger` row (`balance_before: 977923.95` → `balance_after: 1000000.00`, timestamped to match the wallet's real `updated_at`, not "now") — no balance was changed, only the missing audit trail was restored. The row's `metadata` documents it as a backfill and why. A corresponding `audit_logs` entry (`BACKFILL_LEDGER_ENTRY`) records the correction itself. Re-ran the reconciliation endpoint afterward: `status: RECONCILED`, 0 drifted users. Test admin account used to query this cleaned up afterward.

## Phase C — Performance

- [x] **C1. Bound every unbounded query.** Audited every list-style route in `adminApi.ts`. Most were already bounded (`/kyc/queue` LIMIT 200, `/orders/monitor` capped `limit` param, `/risk/alerts` LIMIT 100, `/funds/requests` LIMIT 100, `/executions/provenance` already paginated) — the brief's original "6×/3× unbounded" count was against the whole repo, not just admin routes, and most of that turned out to already be per-user-scoped internal queries (positions/holdings for one customer), not platform-wide scans. Three genuine, currently-unbounded findings fixed:
  - **`GET /kyc/applications`** — zero `LIMIT` at all (every KYC application platform-wide), plus an N+1 query firing one extra round trip per application to fetch its documents. Added `limit`/`offset`/`status` pagination and batched the documents lookup into one `WHERE kyc_application_id = ANY($1)` query. Added supporting indexes (migration `024`): `kyc_applications(submitted_at DESC)`, `kyc_documents(kyc_application_id)` (the latter had no index at all beyond its primary key).
  - **`GET /permissions/users`** — returned every row in `users` with no `WHERE` clause, including every plain customer account, on a screen whose entire purpose is staff role/permission management. At the brief's 1,000+-user scale target this would return the whole platform on every page load. Restricted to non-`USER` roles, which bounds the result by staff headcount instead of customer count (verified: dropped from returning the whole table to 13 staff rows on the current dataset).
  - **`GET /executions/provenance`** — the client-supplied `limit` query param was passed straight through with no cap, so a caller could request an arbitrarily large page. Capped at 500.
  - **Most consequential finding, outside the original C1 scope**: while adding migration `024`, discovered this codebase's migration runner (`db/schema.ts runMigrations`) has **no migrations-applied tracking table at all** — every `.sql` file re-runs unconditionally, oldest-filename-first, on every single server startup. That makes every migration a standing, permanent idempotency contract against whatever data currently exists, not a one-time script. Two existing migrations violated it: `017_update_wallet_ledger_check_constraint.sql` and `020_closed_trades_admin_square_off_reason.sql` each set a CHECK constraint that a *later* file (`023`, `021` respectively) legitimately widens — but because the earlier file re-applies its own narrower definition on every restart (it runs first, alphabetically), the very first time real data contained a value only the later file allowed, the earlier file's `ALTER TABLE ADD CONSTRAINT` would fail (Postgres validates against all existing rows), crash-looping the entire server on every future deploy. This wasn't hypothetical — it actually happened live during this task (triggered by the `MARGIN_RESET` backfill row from B3), taking the container down. Fixed both migrations to include the full, current value set so they're no longer narrower than reality; verified with a full clean redeploy (all 25 migration files re-ran successfully in order, container healthy). **This class of bug can recur with any future constraint-widening migration** — worth a standing rule: a new migration that widens a CHECK constraint must also update the *earliest* file that created/last-set that same constraint name, not just add a new file, given there's no tracking table to make "already applied" migrations inert.
- [x] **C2. Server-side filtering and search.** The main large-table list routes already have adequate server-side filters, verified while reading through them for C1: `/customers` (search/status/role), `/orders/monitor` (status/exchange), `/funds/requests` (status), `/executions/provenance` (userId/symbol/freshness), and now `/kyc/applications` (status, added above). **Not done in this pass**: an audit of the *client* React components to confirm none of them fetch a full list and filter/paginate in the browser instead of using these server-side params — that's a frontend-code question better suited to Phase D (design system migration), which touches every one of these components anyway, rather than a separate pass here.
